# YIJINTOOL

企业经营优化系统

**当前版本：[0.2.0-beta.1](https://github.com/yeungmingyik/business-optimization-system/tree/v0.2.0-beta.1) · 第一阶段测试版**

## 产品介绍

YIJINTOOL 围绕企业客户与订单增长、业务跟进效率和经营数据管理建设。项目源于企业经营优化立项：将分散的客户、销售渠道、产品、订单与付款信息形成可查询、可追溯的业务记录，为管理者了解经营状况、提高资源利用效率提供基础。

第一阶段聚焦销售与客户服务流程，将客户来源、跟进记录、意向产品、订单、付款和物流关联到同一工作台。运营人员维护本人负责的客户与订单，企业老板查看全局业务、分配负责人并管理账号。

当前版本提供经营管理的数据基础；库存采购、完整成本利润核算、资金预算及财务总账属于后续范围。订单付款为人工登记，开票字段记录开票需求，尚未接入真实支付、自动开票或平台消息发送。

### 账号权限

| 角色     | 数据范围                                               | 管理权限                                     |
| -------- | ------------------------------------------------------ | -------------------------------------------- |
| 运营人员 | 本人负责的客户、跟进、订单、付款及运单；共享产品与资料 | 维护本人业务、登记付款、修改本人密码         |
| 企业老板 | 全部客户与订单；共享产品与资料                         | 账号管理、负责人分配、付款更正及全局经营查询 |

草稿始终按当前账号隔离，老板也不能读取其他账号的新客户草稿。客户转交后，订单与运单的访问权限随最新负责人变更。

### 金额规则

- 税率按百分比输入，支持最多四位小数。
- 自动税费 = 商品总额 × 税率 ÷ 100，四舍五入至分。
- 自动含税总计 = 商品总额 + 有效税费 + 运费 + 包装费。
- 税费与含税总计可分别手动修改，也可分别恢复自动计算。
- 登记付款及保持已付款状态的付款更正均须填写收款账号；更正保留历史记录。

## 测试部署

本指南适用于在另一台电脑运行独立的本地验收环境。每台电脑拥有自己的数据库、文件和账号，不会自动同步其他电脑的数据。访问地址为该电脑的 `127.0.0.1`，不是可分享给其他人的公网网址。

前端使用 React、TypeScript、Vite、shadcn/ui 与 Tailwind CSS；后端使用 NestJS 与 PostgreSQL。运单识别运行在 Python Docker 容器中，不需要在 Windows 主机另外安装 Python，也不需要 GPU。

### 首次安装与启动

以下命令均在 **PowerShell 7** 中执行。

```powershell
Set-Location D:\
git clone https://github.com/yeungmingyik/business-optimization-system.git
Set-Location D:\business-optimization-system
./scripts/setup.ps1
./scripts/check-env.ps1
./scripts/start.ps1
```

以上命令取得主分支的最新源码；需要复现指定测试版时，可从页面顶部的版本标签下载源码。收到项目源码压缩包时，应将完整源码解压到 D 盘目录，再从 `setup.ps1` 开始执行。反馈问题时请提供 README 中的版本号及复现步骤。

`setup.ps1` 在缺少 Node.js 时下载并校验官方安装包，默认安装到 `D:\nodejs`；准备项目 pnpm、按锁文件安装依赖，并生成本机 `.env` 与初始老板凭据。**首次运行不要预先将 `.env.example` 复制为 `.env`**，空模板不包含可用密码。已有 `.env` 和账号配置会保留，缺少的 OCR 密钥会补充生成。

`start.ps1` 构建并启动 OCR 容器、下载及校验模型、启动数据库、编译项目、应用数据库迁移，最后启动 API 和网页。首次准备可能需要较长时间；后续使用已有依赖、镜像构建缓存和模型卷。

启动完成后打开 **[http://127.0.0.1:5173](http://127.0.0.1:5173)**。在本机查看初始老板账号：

```powershell
Get-Content ./.local/access.json
```

该文件包含本机随机生成的初始密码，不应提交到仓库或共享。修改密码后，以修改后的密码登录；文件不会自动记录新密码。老板可在“账号管理”中创建其他账号，新建或重置账号按页面要求修改临时密码。

可用以下命令确认服务就绪：

```powershell
Invoke-RestMethod http://127.0.0.1:3000/api/v1/health
Invoke-RestMethod http://127.0.0.1:8000/health
docker compose ps
```

### 日常启动与停止

先启动 Docker Desktop，然后执行：

```powershell
Set-Location D:\business-optimization-system
./scripts/start.ps1
```

停止普通环境的前后端及容器，保留数据库和模型：

```powershell
./scripts/stop.ps1
docker compose stop postgres ocr
```

若自动化测试仍在运行，不要停止共享的 OCR 服务。`stop.ps1` 只停止本项目登记的 API 和网页进程，不停止 Docker Desktop。

### 更新已有环境

先停止应用，并备份数据库、`.data/uploads` 以及本机配置。数据库位于 Docker 数据卷，**仅复制仓库目录不构成数据库备份**。保留已有 `.env` 和数据卷，不要为了升级重新生成密码或删除数据库。

```powershell
Set-Location D:\business-optimization-system
./scripts/stop.ps1
./scripts/stop.ps1 -Test
git pull --ff-only
./scripts/setup.ps1
./scripts/start.ps1
```

本地有未提交修改时，先处理 Git 提示后继续，不执行强制重置。使用源码压缩包更新时，保留本机配置和数据目录后替换功能源码，再执行 `setup.ps1` 和 `start.ps1`。启动过程会应用新增迁移；不提供自动降级迁移，不用旧版源码直接回退已升级的数据结构。

### 自动化测试

以下命令使用独立的 `business_test` 数据库和 `.data/test-uploads`，会创建测试记录。先完成首次安装；测试数据库与普通验收数据库分别使用不同端口和数据卷。

```powershell
Set-Location D:\business-optimization-system
. ./scripts/enter-env.ps1
./scripts/pnpm.ps1 exec playwright install chromium
./scripts/start.ps1 -Test
./scripts/pnpm.ps1 check
./scripts/pnpm.ps1 test:api
./scripts/pnpm.ps1 test:ocr
./scripts/pnpm.ps1 test:e2e
```

测试网页为 `http://127.0.0.1:5174`。其专用测试账号是 `test-owner`，密码是 `TestOwner2026!Local`，只用于隔离测试库；不用于普通验收或生产环境。

`check` 包含类型检查、生产构建、单元测试和文件解析测试。`test:api` 覆盖真实数据库下的业务与权限接口；`test:ocr` 验证识别服务边界；`test:e2e` 执行浏览器流程，包含调用真实 OCR 服务的合成运单测试。真实模型用例与模拟识别响应的交互用例分别保留。

测试报告写入 `.artifacts/tests/`。可查看 `vitest-results.json`、`browser-results.json`，以及 `playwright-report/index.html`；失败截图与 trace 位于 `browser-results/`。

测试完成后：

```powershell
./scripts/stop.ps1 -Test
docker compose --profile test stop postgres-test
```

两套环境均不再使用识别时，再执行 `docker compose stop ocr`。不要使用 `docker compose down -v` 作为日常停止方式，该参数会删除持久化数据卷。

### 常见问题

| 现象或错误                                                                  | 处理方法                                                                                                                         |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `127.0.0.1:5173` 无法访问                                                   | 启动 Docker Desktop，在项目目录运行 `./scripts/start.ps1`；查看终端是否报告启动完成                                              |
| `POWERSHELL_7_REQUIRED`                                                     | 改用 `pwsh`，不要使用 Windows PowerShell 5.1                                                                                     |
| `D_DRIVE_REQUIRED` / `D_DRIVE_LINK_REQUIRED`                                | 检查仓库、Node、缓存及链接实际目标均位于 D 盘                                                                                    |
| `NODE_VERSION_UNSUPPORTED` / `NODE_INSTALL_DIRECTORY_EXISTS`                | 使用支持的 Node 24.x；已有目录不会被覆盖，可在当前终端设置 `$env:BOS_NODE = 'D:\yijintool-runtime\node\node.exe'` 后重新执行安装 |
| `DOCKER_STORAGE_CONFIGURATION_REQUIRED` / `D_DRIVE_DOCKER_STORAGE_REQUIRED` | 完成 Docker Desktop 的 D 盘数据目录配置并应用设置                                                                                |
| `PORT_IN_USE`                                                               | 先确认已有实例是否可用；需要重启时运行 `stop.ps1`，测试实例则加 `-Test`                                                          |
| `OCR_BUILD_FAILED` / `OCR_START_FAILED`                                     | 检查网络、Docker 可用资源及端口 8000；查看 `docker compose logs --tail 100 ocr-models ocr`，修复后运行 `./scripts/setup-ocr.ps1` |
| `DATABASE_START_FAILED`                                                     | 确认 Docker 已运行并使用 Linux containers；查看 `docker compose logs --tail 100 postgres`                                        |
| `APPLICATION_START_FAILED`                                                  | 查看 `.artifacts/logs/development-api-error.log`、`development-web-error.log`；测试实例对应 `test-*` 文件                        |
| 已上传图片但识别失败                                                        | 检查 OCR 健康状态；可保留附件并手工录入，也可稍后重试。识别候选需人工核对                                                        |
| `git clone` 提示仓库不存在或无权限                                          | 使用已获得该私有仓库访问权限的 GitHub 账号                                                                                       |

## 验证范围与当前限制

本轮收货地址、客户草稿、税率及金额调整、运单图片识别、收款账号五组功能已完成主要操作链验证；这不代表第一阶段全部正式验收场景已通过。

- 已验证客户地址及草稿、订单金额、付款更正和数据归属权限的 API 与浏览器流程。
- 已验证 PaddleOCR 对一张德邦真实照片和合成顺丰运单的识别、确认及保存流程；尚无多承运商真实样本准确率结论。
- 已验证识别取消、迟到响应、失败重试、超时和候选人工修改。识别耗时取决于图片与电脑配置。
- 已验证旧库迁移后原有客户、订单金额和付款记录保留，以及重复、并发迁移的幂等性。
- 已验证 WebP 上传读回、10 MiB 精确边界、单物流 5 张和待保存 30 张限制、删除及过期附件的物理回收；定时触发采用模拟计时器配合真实测试数据库及文件。
- 本机三次首屏样本的字体传输均为 297184 字节，低于 350 KiB 预算；完整规模负载及真实低端设备性能仍需结合部署环境验收。
- 100 条明细订单在此前的 4 倍 CPU 降速模拟下出现打开和滚动卡顿；当前优化版本尚未完成该规模的最终复验，不能判定该压力场景通过。日常验收按实际业务的 20 条以内订单开展。
- 已完成本机功能测试，以及 D 盘干净源码目录中的依赖安装、环境路径检查和前后端构建。该隔离安装检查未启动数据库或 OCR，尚未在第二台实体电脑完成独立验收；macOS、Linux 主机及 Windows ARM 不在本指南已验证范围内。
- 企业微信、其他平台自动同步、真实支付、自动开票及库存财务模块不属于当前交付能力。

最终版本对 20 条明细订单进行了两组各 50 轮的本机实验室测试，每组另测 20 秒连续滚动及输入：

| 指标                         | 本机正常运行 | 浏览器 CPU 降速 4 倍 |
| ---------------------------- | -----------: | -------------------: |
| 核心交互响应 p95             |        24 ms |                88 ms |
| 完整订单表单就绪 p95         |       115 ms |               423 ms |
| 滚动帧间隔 p95               |      16.7 ms |              16.7 ms |
| 测量期间超过 100 ms 的长任务 |         0 次 |                33 次 |
| 浏览器及 API 错误            |            0 |                    0 |

测试使用 Ryzen 5 3600、16 GB 内存、Windows、Chromium、生产构建及 10 Mbps / 80 ms 模拟网络。交互响应衡量界面对操作的反馈，不能替代完整表单就绪时间；这些合成测量也不是真实用户 INP。两组响应与滚动指标达标，但降速模拟的全阶段长任务指标仍未通过，需在实际电脑继续验收，不能据此宣称全部性能要求已满足。

当前入口用于本地测试，不是公网生产部署方案。GitHub 源码仓库或 GitHub Pages 本身不会运行本项目所需的 NestJS、PostgreSQL 和 OCR 服务。

## 如何参与验收

使用测试客户与测试收款账号。按以下顺序操作，记录版本号、电脑配置、浏览器版本、实际结果和失败时的复现步骤；截图遮盖密码、收款账号及个人信息。

| 步骤          | 操作                                                                                                                                          | 预期结果                                                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1. 新电脑启动 | 按“首次安装与启动”准备一台 Windows 电脑，首次运行后关闭应用，再次启动                                                                         | 网页及 OCR 健康检查正常；重启后已有账号、客户和订单保留；依赖、上传和 Docker 数据位于 D 盘                                         |
| 2. 角色隔离   | 老板创建运营 A/B，使用三个独立浏览器配置文件分别登录；A/B 各建一个客户和订单，互换详情链接；老板将 A 的客户转交 B                             | 运营仅访问本人数据；老板可见全部；转交后 A 的客户、订单和运单链接不可再访问，B 可访问                                              |
| 3. 地址与草稿 | 新增客户分别填写公司地址与收货地址，只填部分信息后关闭、重开及刷新，再补齐保存；随后创建订单                                                  | 草稿可续写，其他账号看不到；两类地址分别保存，订单带入收货地址；修改客户地址后旧订单地址不变                                       |
| 4. 金额与收款 | 建立商品总额 200 元的订单，税率 13%、运费 10 元、包装费 2 元；税费改为 20 元，再把总计改为 230 元，分别恢复自动；登记付款并由老板更正收款账号 | 自动税费 26 元、总计 238 元；手工税费时总计 232 元；手工总计 230 元；恢复后回到 238 元；收款账号必填，更正历史可追溯，运营不能更正 |
| 5. 运单与识别 | 上传 JPG/PNG/WebP，逐一尝试识别、编辑候选、取消、确认并保存；准备德邦、顺丰、中通各 5–10 张具有不同清晰度/倾斜角度的测试运单                  | 确认前物流字段不被覆盖；确认后号码及图片随订单保存；逐张人工比对完整号码，记录正确/错误/未识别及耗时。小样本结果不作为整体准确率   |
| 6. 实际工作流 | 连续完成客户跟进、下单、登记付款、更新物流及查询；在日常使用的屏幕上测试键盘操作、200% 字号与 20 条以内明细订单；实际业务超过 20 条时另行记录 | 功能关联和结果符合实际业务；按钮、字段可操作；出现卡顿时记录所在页面、明细数量、操作和是否正在识别                                 |

问题反馈建议包含：`版本 / 电脑与浏览器 / 使用角色 / 复现步骤 / 预期结果 / 实际结果 / 截图或日志`。OCR 问题另附测试图片和人工核对的完整运单号；不要提供登录密码或真实业务密钥。
